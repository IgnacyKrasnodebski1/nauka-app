# Recall — API (apps/web, Next.js route handlers)

Wszystkie endpointy poza webhookiem wymagają nagłówka `Authorization: Bearer <supabase access_token>`.
Błędy: JSON `{ error: string, code?: string, ...extra }` z odpowiednim statusem (401, 402 limit planu, 400, 409 `busy`, 410 `tutor_disabled`, 500). Nowe pola są tylko dodawane (np. `reason`, `tokens`); istniejące kody i kształty się nie zmieniają.

## POST /api/generate
Tworzy **temat** w przedmiocie użytkownika. Body:
```json
{ "subjectId": "uuid", "materialIds": ["uuid"], "text": "opcjonalny wklejony tekst",
  "options": { "stage": "liceum", "subjectName": "Biologia", "mode": "materials" | "prompt", "hint": "fotosynteza, klasa 7", "levels": 4, "lang": false, "viz": true, "aiConsentV": 1 } }
```
`mode=materials` wymaga `materialIds.length > 0 || text`; `mode=prompt` wymaga `options.hint`. `options.aiConsentV` (opcjonalne, liczba całkowita 1–999) to wersja tekstu zgody na AI zaakceptowanej w Cramfoxie (build 7+); trafia tylko do `generations.options`, a zła wartość jest pomijana bez błędu. **`options.levels` jest ignorowane** (AUDYT P1-29): serwer zawsze prosi o 4 poziomy (w trybie `materials` do 6 przy obszernym materiale); pole zostaje w schemacie, żeby stare klienty dalej przechodziły walidację. API sprawdza, że `subjects.owner_id = user`. Limity z `PLANS[plan]` (`maxFileMb` na plik → 400 `file_too_big`, `{ name, maxMb }`) plus łącznie max 150 MB materiałów na jedną generację (→ 400 `too_much_material`, `{ maxMb }`). `materials.size_bytes` zapisuje klient, więc służy tylko do wczesnego odrzucenia — oba limity są sprawdzane ponownie na prawdziwym rozmiarze pobranych plików (pobieranie po 3 pliki naraz, przerwane po przekroczeniu sumy). PDF-y (oraz zdjęcia, gdy razem mają > 15 MB) `@nauka/ai` wgrywa raz na generację do Anthropic Files API (`expires_in_seconds: 7200`) **przed naliczeniem** (wgranie i `count_tokens` są darmowe), w wywołaniach Messages odwołuje się do nich przez `file_id` i usuwa je po zakończeniu (także gdy limit odmówi); błąd wgrywania → 500 `reserve_failed` z `reason: "ai_upload"`, bez naliczenia. Synchroniczne (`maxDuration = 300`). Całą sekwencję prowadzi `handleGenerationRequest()` z `@nauka/ai` (`packages/ai/src/pipeline.ts`); trasa wstrzykuje tylko dostęp do bazy. Temat zapisuje RPC `finish_generation` (position = max(position) + 1 w przedmiocie, czyli liczba tematów, dopóki żadnego nie usunięto; `source` = mode, `generation_id`) w tej samej transakcji co status `done`.
Odpowiedź 200: `{ "generationId": "uuid", "topicId": "uuid", "topic": Topic, "demo": boolean }` (bez zmian).
402: `{ error, code: "limit_reached", used, limit }` (bez zmian, także wartości `used` 999999 / 1999999). Od backend/0007 limit planu dodaje `scope`: `"month"` (pro: limit miesięczny) albo `"lifetime"` (free: darmowe generacje na zawsze, domyślnie 2 — `used`, `limit` to licznik na zawsze; build 6 czyta tylko `used`/`limit` i pokaże swój tekst miesięczny z dobrymi liczbami, „2 z 2”).

**Typy materiałów** (`materials.mime`, `UPLOAD_MIME` w `@nauka/shared/plans`): zdjęcia jpg/png/webp/gif, PDF, txt/md (`AI_MIME`, idą do AI bez zmian) oraz PowerPoint `.pptx` (`PPTX_MIME` = `application/vnd.openxmlformats-officedocument.presentationml.presentation`). Stare `.ppt`, Keynote i Word nie są obsługiwane.
PPTX `@nauka/ai` (`prepareMaterials` → `extractPptx`, bez natywnych zależności, `fflate`) zamienia na materiał tekstowy „Slajd N: tytuł / treść / tabele / SmartArt / Notatki prowadzącego: …” (kolejność z `presentation.xml`, slajdy ukryte pomijane, stopki i numery slajdów pomijane) plus obrazy ze slajdów jako osobne zdjęcia z etykietą „<plik> — slajd N”. Obrazy: tylko png/jpg/gif/webp, 15 kB–5 MB, ≤ 2000 px (wymiary z nagłówka pliku), deduplikacja po SHA-1, obraz na > 40% slajdów (min. 3) to logo/tło i jest pomijany; EMF/WMF/TIFF/SVG pomijane. Łącznie maks. 40 obrazów na generację razem ze zdjęciami (zdjęcia mają pierwszeństwo, obrazy ze slajdów wybierane równomiernie z całej prezentacji); gdy któreś zdjęcie ma > 2000 px — maks. 20. Limity bezpieczeństwa: 3000 elementów ZIP, 200 MB po rozpakowaniu (deklarowane, na prezentację), 5 MB na rozpakowywany element XML, 300 slajdów, 400 tys. znaków tekstu (reszta pomijana z adnotacją). XML czytany liniowym tokenizerem (`indexOf`, bez regexów z cofaniem po całej części), znacznik otwierający max 16 kB. Wspólny budżet wszystkich prezentacji jednej generacji (`PPTX_BUDGET`): 100 MB rozpakowanego XML, 200 mln znaków XML, 30 s parsowania (przekroczenie → 400 `bad_pptx`) oraz 200 MB rozpakowanych obrazów i 80 MB zachowanych obrazów ze slajdów (ponad to dalsze obrazy są pomijane, tekst zostaje). Limit 40 obrazów stosowany już przy rozpakowaniu (każda prezentacja dostaje część tego, co zostało). Gdy wśród materiałów jest prezentacja, prompt prosi o `src_page` = numer slajdu.

**Kolejność** (nic nie jest naliczane, jeśli materiały są złe albo nie da się zacząć): walidacja body → przedmiot → limity plików (`too_many_files`, `bad_materials`, `file_too_big`, `too_much_material`) → typ każdego materiału z `UPLOAD_MIME` (inaczej 400 `bad_materials`) → tylko-do-odczytu sprawdzenie limitu (RPC `generation_quota`: wykorzystany limit planu — free na zawsze, pro w miesiącu — albo ≥ 20 generacji konta w 24 h → 402 `limit_reached`; trwająca generacja konta → 409 `busy`; zanim cokolwiek zostanie pobrane; błąd RPC = pominięcie, i tak sprawdzi rezerwacja) → pobranie plików z Storage (błąd → 500 `download_failed`; prawdziwy rozmiar → 400 `file_too_big` / `too_much_material`) → rozpakowanie PPTX (błędy 400 poniżej) → budżet tekstu: znaki tekstu prezentacji + plików tekstowych + wklejonego tekstu > 1,5 mln (`MAX_TEXT_CHARS_PER_GENERATION`) → 400 `too_long` → **przygotowanie dla AI**: wgranie PDF-ów (i dużych zestawów zdjęć) do Files API i policzenie promptu (`count_tokens`, tylko gdy są pliki; sam wklejony tekst ma limit 200 tys. znaków) → powyżej `MAX_INPUT_TOKENS` = 150 000 tokenów 400 `too_long` z `tokens`, `maxTokens` → **naliczenie**, tylko w ciągu 75 s od startu żądania (`CHARGE_BY_MS`, sprawdzane przed wgraniem do Files API i drugi raz tuż przed naliczeniem; później → 500 `download_failed` z `reason: "slow_intake"` bez naliczenia — Cramfox uznaje brak wiersza po 90 s za „generowanie nie ruszyło”): RPC `reserve_generation` (backend/0007) w jednej transakcji z blokadami doradczymi konta, adresu e-mail (plan free) i serwera; plan czyta sama z `profiles.plan`: `busy` → limit dzienny 20 → limit planu (free: darmowe generacje **na zawsze**, liczone po skrócie adresu e-mail w `free_generation_ledger`, limit z `app_config.free_lifetime_generations`, domyślnie 2; pro: miesięczny z `PLANS`) → globalny z `app_config.generation_global_daily_cap`, domyślnie 30 (większa z liczb: wiersze `generations` z doby albo `generation_ledger` — licznik bez powiązania z kontem, więc usuwanie kont go nie zeruje) → dla free pula free w limicie globalnym (`app_config.free_global_daily_cap`, domyślnie 20 z 30; wiersze `free_generation_ledger` z doby — reszta zostaje dla pro), wszystkie sprawdzane **przed** podbiciem licznika; potem wiersz `generations` (`running`), wpis w `generation_ledger`, dla free wpis w `free_generation_ledger` i `usage + 1` (odmowa niczego nie zmienia) → AI → RPC `finish_generation` (temat + `done` + koszt w jednej transakcji). Gdy `finish_generation` się zatwierdzi, a zginie tylko jego odpowiedź, trasa sprawdza wiersz `generations` i odpowiada 200 z tematem (zamiast 500 dla opłaconej lekcji). Sprzątanie Files API i oznaczanie porażki dostają tylko czas do startu + 285 s (`RESPOND_BY_MS`), żeby JSON zawsze wyszedł przed 300 s. Błąd po naliczeniu (AI, zapis) nie zwraca generacji (zwroty czekają na decyzję D4, AUDYT P1-33); wiersz dostaje `failed`, błąd i koszt tego, co zużyto. **Wyjątek (incydent 2026-10-16, backend/0009):** AI niedostępne po naszej stronie (`ai_unavailable`, niżej), zanim jakiekolwiek wywołanie AI zaczęło odpowiadać — trasa woła RPC `release_generation` **zamiast** oznaczania porażki (jedna transakcja: wiersz `generations` → `failed` z `refunded_at` i `error` = `released:ai_unavailable: <oryginalny błąd>` (≤ 200 znaków, bez sekretów), `usage − 1` w miesiącu wiersza, wiersz `free_generation_ledger` unieważniony i oznaczony `refunded_at`, wpis `generation_ledger` unieważniony) i odpowiada `charged: false`. Dzięki tej kolejności klient odzyskujący przerwaną generację nigdy nie widzi wiersza `failed`, który jeszcze nie jest zwrócony. Bez 0009 albo gdy RPC się nie uda (albo nie odpowie w czasie): dopiero wtedy `failed` z `error` = `ai_unavailable: …`, naliczenie zostaje i odpowiedź mówi `charged: true`. Limit 20 generacji konta na dobę dalej liczy zwróconą próbę (bezpiecznik przed nadużyciem) — przy długiej awarii użytkownik, który ponowi 20 razy, dostanie `402 limit_reached` (dzienny, „Na dziś wystarczy”), choć każda porażka mówiła „Limit się nie zmienił” (świadoma decyzja; alternatywa: nie liczyć wierszy z `refunded_at` i dodać osobny limit zwróconych prób).

**Pole `charged` (nowe, addytywne).** Każda odpowiedź z błędem z sekwencji generowania mówi, czy próba liczy się do limitu: `false` — przed naliczeniem albo zwrócona (wtedy też `refunded: true`), `true` — naliczona. Błędy z trasy przed sekwencją (`no_config`, `unauthorized`, `bad_request`, `not_found`, `too_many_files`, zadeklarowane rozmiary) go nie mają — nigdy nie są naliczone. Starsze klienty go ignorują (build 7 czyta `refunded` i `generationId`).

**Błędy AI (`@nauka/ai`, `classifyAiError`).** Po naszej stronie → `ai_unavailable`: 401/403 (klucz, uprawnienia), 404 (model albo plik — konfiguracja), 408, 429, 5xx z 529 włącznie, 400 o rozliczeniach konta („credit balance”), zerwane połączenie, te same typy błędów w zdarzeniu `error` strumienia, termin 270 s bez żadnej odpowiedzi AI. Oryginalny błąd (status, typ, `request-id`, bez sekretów) idzie do logów i do `generations.error`. Przed naliczeniem: wgranie do Files API (PDF-y, duże zestawy zdjęć) odrzucone po naszej stronie (401/403/429/5xx/sieć — przy nieważnym kluczu i PDF-ie to pierwsze wywołanie AI) albo `count_tokens` z 401 → 503 `ai_unavailable`, `charged: false`, bez `generationId`; inne błędy `count_tokens` tylko pomijają kontrolę tokenów, jak dotąd, a inne błędy wgrania (np. 400 o pliku) → 500 `reserve_failed` z `reason: "ai_upload"`, jak dotąd. Pominięty poziom trafia do logu z oryginalnym błędem (status, typ, `request-id`). Materiał → bez zmian: 413 i „prompt is too long” → `too_long`; 400/415/422 o obrazie albo PDF → `api` z `reason: "material"`; inne 4xx → `api` bez `reason`. Pojedynczy poziom z `ai_unavailable` jest pomijany jak przy `api`.

**Termin (AUDYT P1-4).** Każde wywołanie AI (Files API, `count_tokens`, plan, poziomy, review) dostaje ten sam `AbortSignal`, który odpala się o starcie żądania + 270 s (`GENERATION_DEADLINE_MS`), i `maxRetries` 1, gdy do terminu zostało > 120 s, inaczej 0. Poziom przerwany terminem jest pomijany jak inny nieudany poziom (gotowe poziomy zostają, review dostaje tylko pozostały czas); gdy nie zostało nic, odpowiedź to 500 `lost` z `reason: "ai_timeout"` i `generationId`. Kod celowo **nie** jest `timeout` (klient pokazałby „Materiał nie został wysłany”, co po naliczeniu jest nieprawdą). Jeśli pobieranie, rozpakowanie, wgranie do Files API albo `count_tokens` trwały dłużej niż 75 s od startu żądania (zostało < 195 s = `MIN_AI_TIME_MS`), serwer kończy przed naliczeniem: 500 `download_failed` z `reason: "slow_intake"` (sprawdzane przed wgraniem i tuż przed naliczeniem). Wiersze `queued`/`running` starsze niż 8 min zamyka sprzątacz w pg_cron (`cramfox-sweep-generations`, co 5 min) jako `failed`.

**Pamięć podręczna promptu (AUDYT P1-2).** Wywołanie planu nie ma `cache_control` (inny format wyjścia, nikt nie czyta jego wpisu). Poziom 1 startuje pierwszy; pozostałe poziomy startują, gdy oba wywołania poziomu 1 (rdzeń i zadania) zaczną strumieniować (wpis w cache jest wtedy czytelny), najdłużej po `WARM_UP_CAP_MS` = 30 s. Wejście spada z ok. 13–16× do ok. 4,5× prefiksu z materiałem. Gdy poziom 1 od razu padnie z błędem kończącym generację (odmowa, za długi materiał), pozostałe poziomy w ogóle nie startują.

**Koszt (AUDYT P1-3).** Kolumny `generations` (backend/0007): `opus_input`, `opus_cache_write`, `opus_cache_read`, `opus_output` (model generujący: plan i poziomy), `review_input`, `review_output`, `cost_usd numeric(8,4)` i `quality jsonb` (statystyki jakości, `warmupMs`, `durationMs`, `inputTokensCounted`, `calls`, `partialCalls`, przy błędzie `failedPhase`). Koszt liczy `@nauka/ai` (`cost.ts`, tabela `MODEL_PRICES`) według modelu, który faktycznie odpowiedział (przy server-side fallback z `usage.iterations`). Wywołania przerwane terminem są liczone z ostatniego stanu strumienia. Zapisywane także przy `failed`. Stare `input_tokens` / `output_tokens` dalej są wypełniane (suma wszystkich tokenów). Dzienne sumy: widok `generation_cost_daily` (tylko service role / SQL Editor).

**Mapowanie dla klienta (Cramfox).** `ai_unavailable` (klient z tej zmiany): „Tworzenie lekcji chwilowo nie działa — To problem po naszej stronie, nie z Twoim materiałem. Limit się nie zmienił — spróbuj ponownie za kilka minut.” (przy `charged: true` zamiast tego „Ta próba liczy się do …”), z „WRÓĆ DO MATERIAŁU”, bez ponawiania; „Plik jest za duży albo zabezpieczony” tylko przy `api` z `reason: "material"` (starszy backend: `AI: 400/413/415/422` z treścią o obrazie albo PDF). Build 7 pokaże `ai_unavailable` jako nieznany kod ≥ 500: „Coś poszło nie tak po stronie serwera — Nie udało się utworzyć lekcji. Limit się nie zmienił.” (czyta `refunded`), bez `generationId` (przed naliczeniem) „… Spróbuj ponownie za kilka minut.”, przy `charged: true` + „Ta próba liczy się do …” (prawda). **Starsze buildy — znane nieścisłości (na korzyść użytkownika, serwer ich nie naprawi, bo oba buildy wysyłają to samo żądanie):** build 6 przy każdym nieznanym kodzie ≥ 500 dopisuje „Ta próba liczy się do miesięcznego limitu”, więc `ai_unavailable` — także zwrócone albo w ogóle nienaliczone (wgranie do Files API, `count_tokens` 401) — pokaże „Coś poszło nie tak po stronie serwera — Nie udało się utworzyć lekcji. Ta próba liczy się do miesięcznego limitu.” (nieprawda; przed tą zmianą awaria wgrania dawała prawdziwe „Serwer chwilowo nie działa … Limit się nie zmienił”); build 7, gdy odpowiedź zginie, a odzyskiwanie (`recoverJob`) znajdzie zwrócony wiersz (`released:…`), zgłosi `generation_failed`: „AI nie dało rady z tym materiałem … liczy się do limitu”. Klient z tej zmiany czyta prefiks `released:ai_unavailable` / `ai_unavailable:` i mówi prawdę. Build 6 obsługuje resztę bez zmian: `busy` → „Coś poszło nie tak / Spróbuj ponownie” (ogólny 4xx); `lost` → „Generowanie się nie dokończyło … liczy się do limitu” (prawda); `reserve_failed` i `download_failed` → „… Limit się nie zmienił” (prawda); `too_long` bez `generationId` → „… Limit się nie zmienił” (prawda). Build 7 może dodać: `busy` → „Tworzę już inną lekcję — poczekaj, aż skończę” (+ przejście do ekranu postępu); `lost` z `reason: "ai_timeout"` → „Tworzenie lekcji trwało za długo … Spróbuj z mniejszą ilością materiału” (+ limit); `too_long` z `tokens` → „Materiał ma ok. N stron tekstu za dużo na jedną lekcję — podziel go”; `reserve_failed` z `reason: "ai_upload"` → „Serwer AI chwilowo nie przyjmuje plików”. Odrzucenia z limitów konta (backend/0008): wysyłka do Storage → 403/400 „new row violates row-level security policy” (dzienny limit 100 plików / 500 MB), zapis do `subjects` / `materials` → PostgREST 400 z kodem `23514` i komunikatem `subject_limit` / `materials_daily_limit`; build 6 pokazuje wtedy ogólny błąd wysyłki. Darmowe generacje na zawsze (`402 limit_reached` z `scope: "lifetime"`): build 6 pokazuje „Limit na ten miesiąc wykorzystany — Wykorzystano 2 z 2 … Limit odnowi się 1. dnia miesiąca” (liczby dobre, data odnowienia nieprawdziwa — inaczej się nie da bez zmiany buildu 6), a dzięki lustrzanym polom `/api/me` blokuje już przed aparatem; build 7: „Wykorzystano obie darmowe lekcje — Możesz dalej uczyć się z przedmiotów, które masz.” (konto bez przedmiotów: „Na tym koncie nie da się teraz utworzyć nowej lekcji.”), a przy `quota.globalOpen: false` mówi „Serwer ma teraz bardzo dużo pracy … Spróbuj później” jeszcze przed aparatem

**Liczba poziomów.** Serwer używa zawsze `levels = 4` (`GENERATION_LEVELS`; wartość z żądania jest ignorowana). To liczba typowa, nie sztywna. W trybie `materials` konspekt dobiera liczbę poziomów do objętości materiału: mniej przy krótkim, więcej przy obszernym — najwyżej `levels + 2`, czyli 6. W trybie `prompt` limitem jest 4. Nadmiar poziomów jest obcinany z ostrzeżeniem w logu. Poziomy generują się równolegle, więc czas prawie się nie zmienia; koszt rośnie z liczbą poziomów. Jeśli generowanie jednego poziomu się nie uda (ucięta albo nieprawidłowa odpowiedź, błąd API, termin 270 s), ten poziom jest pomijany, a reszta tematu zostaje zapisana. Odmowa AI, za duży materiał albo niepowodzenie wszystkich poziomów nadal kończą się błędem.

**Kontrola jakości.** Konspekt wypisuje w `scope` każdego poziomu punkty kluczowe z całego materiału. Każdy poziom dostaje swoje punkty i zakresy pozostałych poziomów. Przegląd (Sonnet, jedno wywołanie na poziom) poprawia pytania quizu i wyjaśnienia `e`, a zadaniom wystawia tylko werdykt zostaw/usuń, przy czym na poziomie zostają co najmniej 2 zadania. Przed zapisem kod usuwa jeszcze typowe podpowiedzi w zadaniach i odwołania do liter opcji w `e`, a także czyści `real`, jeśli tylko powtarza `body`. Pokrycie punktów kluczowych trafia do logu jako `[generate] coverage {...}`.

**Wizualizacje dawek (`options.viz`).** Opcjonalne; wysyła je tylko klient, który umie je wyświetlić (Cramfox). Bez `options.viz: true` prompt i gramatyka są bajt w bajt takie jak przed wizualizacjami, a odpowiedź nie zawiera pola `viz`. Z `options.viz: true` każda dawka (`levels[].feed[]`) może mieć opcjonalne pole `viz` — unia po `type` (każda gałąź może mieć `caption` ≤ 120 znaków):

| `type` | Pola |
|---|---|
| `timeline` | `items: [{ when ≤ 24, label ≤ 80 }]` × 3–7 |
| `compare` | `a ≤ 40`, `b ≤ 40`, `rows: [{ k ≤ 40, a ≤ 80, b ≤ 80 }]` × 2–5 |
| `cycle` | `steps: string ≤ 60` × 3–6 |
| `flow` | `kind: "cause" \| "process"`, `steps: string ≤ 60` × 2–6 |
| `tree` | `root ≤ 60`, `groups: [{ name ≤ 40, items: string ≤ 50 × 1–5 }]` × 2–4 |
| `bars` | `unit ≤ 12` (może być ""), `items: [{ label ≤ 40, value: liczba skończona ≥ 0 }]` × 2–7 |
| `numbers` | `items: [{ value ≤ 16, label ≤ 80 }]` × 1–4 |

Teksty są zwykłym tekstem (bez HTML i emoji), ale klient i tak musi je escapować. Serwer (`parseViz`) przycina teksty do limitów, waliduje (`VizSchema`), sprawdza ugruntowanie (etykiety w tekście poziomu, liczby i daty w `body`/`real` tej dawki) i zostawia najwyżej ceil(liczba dawek / 2) wizualizacji na poziom; reszta jest odrzucana bez błędu. Statystyki trafiają do logu jako jedna linia `[generate] viz {"kept",…,"schema","grounding","cap","cleared","doses"}`. Starsze tematy i klienci bez obsługi `viz` działają bez zmian (pole jest opcjonalne; `vizText()` daje wersję tekstową, której używa m.in. korepetytor).
Gdy brak `ANTHROPIC_API_KEY` → tryb demo (przykładowy temat, `tagline` „DEMO”).

**Kluczowe punkty (`content.keyPoints`, Cramfox, od backend/0010).** Opcjonalne pole tematu zapisywane w tej samej generacji (bez osobnego wywołania i bez zmiany kształtu żądania/odpowiedzi — punkty po prostu są w zwróconym temacie i w `topics.content`). Konspekt wypisuje 6–15 „punktów do opanowania” całego materiału; każda fiszka, pytanie i zadanie dostaje w generacji tag `p` (klucz punktu); `buildKeyPoints()` w `finalize.ts` składa punkty **po** filtrowaniu, więc indeksy są ostateczne.

| Pole | Reguła |
|---|---|
| `id` | `p1`…`p15`, unikalne, w kolejności wyświetlania |
| `title` | 1–120, zwykły tekst |
| `short` | 1–24 (etykieta chipa) |
| `summary?` | ≤ 300 |
| `levels` | id poziomów tego tematu, w których leżą elementy punktu (kolejność poziomów) |
| `items` | `[{ kind: "quiz" \| "flashcard" \| "task", level, index }]`, ≥ 3, w tym ≥ 2 pytania lub fiszki |

Niezmienniki: każde pytanie i fiszka tematu w dokładnie jednym punkcie, zadanie w najwyżej jednym; 6–15 punktów (3–15, gdy temat ma < 18 pytań i fiszek). Naprawa: nieznany/pusty `p` → pierwszy punkt konspektu z tym poziomem; za mały punkt łączony z sąsiadem; > 15 → scalanie najmniejszych; id numerowane od nowa. Gdy reguł nie da się spełnić, temat zapisuje się **bez** `keyPoints` (generacja nigdy nie pada przez punkty). Stare tematy i tematy bez punktów: klient i serwer liczą punkt zastępczy na poziom (id `L<levelId>`), identycznie w `topicPoints()` (`@nauka/shared` `media.ts`) i `mapPoints()` (Cramfox `cloud.js`). Statystyki: `generations.quality.keyPoints = { keyPoints, repaired, merged, empty, omitted, reason? }` i jedna linia logu `[generate] keyPoints {…}`.

### POST /api/media/reels — seria rolek (albo jedna rolka) — `maxDuration = 300`
Body: `{ "requestId": "uuid", "topicId": "uuid", "types": ["czym","kto","mit","porownanie","sprawdzian"], "focusPointId": "p3" }`.
- `types`: różne, z `czym | kto | mit | porownanie | pulapki | sprawdzian`; seria 3–6; z `focusPointId` (pojedyncza rolka „ZRÓB ROLKĘ Z TEGO”) dokładnie 1.

Kolejność (przed jakimkolwiek kosztem): 503 `no_config` → 503 `ai_unavailable` (brak klucza Anthropic) → 503 `tts_unavailable` (brak `ELEVENLABS_API_KEY`) → 401 `unauthorized` → 400 `bad_request` → idempotencja (200 / 409 `conflict` dla cudzego id) → 404 `not_found` (temat nie należy do konta) → 400 `no_quiz` (temat bez pytań: każda rolka kończy się pytaniem) → 400 `bad_point` → RPC `reserve_media`:

| Odpowiedź | Kiedy |
|---|---|
| 202 `{ media }` | naliczone; `media.status = "running"`, `progress = { step: "plan", done: 0, total: N }`, praca w `after()` |
| 409 `busy` + `busy: { id, kind, topicId }` | konto ma już tworzenie w toku (< 5,5 min; liczone z `media_ledger`, więc usunięcie materiału w trakcie pracy go nie kończy — wtedy `topicId: null`) |
| 402 `limit_reached` + `reason: "lifetime" \| "month"`, `scope`, `used`, `limit` | pula tworzeń (free: 3 na zawsze, pro: 30 w miesiącu UTC; `app_config`) |
| 402 `limit_reached` + `reason: "daily"` | bezpiecznik: 5 tworzeń na konto w kroczącej dobie (liczą się też nieudane) |
| 402 `limit_reached` + `reason: "global"` | limit serwera (60 / krocząca doba, `app_config`) |
| 503 `media_unavailable` | baza bez 0010 |
| 500 `reserve_failed` | inny błąd bazy |

Praca (do startu żądania + 270 s): plan serii (1 wywołanie Claude, `CRAMFOX_MEDIA_MODEL`) → scenariusze (N równoległych, wspólny prefiks w cache promptu; scenariusz sprawdza `sanitizeStoryboard`, przy błędzie jedna ponowna prośba o tę rolkę; muszą zdążyć 75 s przed terminem) → lektor (ElevenLabs `ELEVENLABS_REEL_MODEL`, głos `ELEVENLABS_VOICE_REEL`, po 3 naraz; przed każdą rolką RPC `tts_budget` — ponad dzienny budżet znaków rolka wypada, a gdy zostanie ich za mało, porażka `tts_budget` ze zwrotem) → pliki → `finish_media` (gdy wiersza już nie ma — materiał usunięty w trakcie — pliki są kasowane, a `release_media` zwraca tworzenie po `media_ledger`). Postęp w wierszu: `progress.step` `plan` → `script` (done/total) → `voice` (done/total) → `save`. Mniej niż 3 dobre rolki w serii (0 przy pojedynczej) = porażka. **Porażka:** odmowa AI → `fail_media` (tworzenie naliczone, `charged: true`); każda inna (AI albo lektor niedostępne, zła odpowiedź AI po jednej poprawce, termin, Storage) → `release_media`: zwrot (`charged: false`, `error` = `released:<kod>:<szczegół>`), pliki usunięte. Kody w `error`: `ai_unavailable`, `tts_unavailable`, `tts_budget`, `invalid_output`, `refusal`, `timeout`, `storage_failed`, `not_finished`. Wiersz `running` starszy niż 8 min zwraca sprzątacz (`timeout:sweeper`).

Pytanie końcowe = istniejące pytanie quizu `levels[level].quiz[index]` (zapis do SRS robi apka). Nazwy plików zachowują numer rolki z planu (po odrzuceniu rolki `n` jest przenumerowane, nazwy nie).

### POST /api/fox — jedna tura rozmowy z lisem — `maxDuration = 60`, synchronicznie
Body: `{ "subjectId": "uuid", "topicIds": ["uuid"], "pointIds": ["<topicId>:p3"], "mode": "explain" | "quiz" | "exam", "step": "start" | "answer" | "hint" | "idk" | "finish", "messages": [{ "role": "fox" | "user", "text": "…" }] }`. `topicIds` 1–8 (tematy tego przedmiotu), `pointIds` ≤ 20 z wybranych tematów (`explain`: dokładnie 1), `messages` ≤ 30, tekst ≤ 1500. Serwer jest bezstanowy: klient przysyła całą rozmowę, a **liczbę tur liczy serwer**: każda wiadomość `user` to odpowiedź, poza samym „Podpowiedz”; samo „Nie wiem” liczy się jako odpowiedź. Klient powinien po turze `hint` / `idk` dopisać tekst chipa jako wiadomość `user` (wtedy liczenie jest dokładne; bez tego `idk` liczy pominięcie tylko w bieżącym żądaniu).

Kolejność: 503 `no_config` / `ai_unavailable` → 401 → 400 `bad_request` → 400 `too_many_turns` (rozmowa już się skończyła) / `bad_step` (np. `answer` bez odpowiedzi ucznia na końcu) → `finish` bez żadnej odpowiedzi (i `finish` w `explain`): **200** `{ reply, next: "end", quota }` bez AI i bez liczenia → 404 `not_found` (przedmiot / tematy nie Twoje) → 400 `bad_point` → RPC `reserve_chat` → 402 `limit_reached` + `reason: "chat_daily" | "chat_global"`, `used`, `limit` → AI (`CRAMFOX_FOX_MODEL`, termin 50 s, cache promptu na system + kontekst) → 200. Porażka AI: wiadomość wraca do licznika (`release_chat`), 503 `ai_unavailable` albo 500 `fox_failed`, `charged: false`.

Tryby (decyduje serwer): **explain** — `start` → prośba o wyjaśnienie punktu; 1. odpowiedź → `verdict` + `feedback { good, gap, wrong, source? }` + dopytanie (`next: "followup"`); 2. → `next: "end"`; `idk` → krótkie wyjaśnienie, `end`. **quiz** — 5 pytań otwartych; każda odpowiedź → `verdict` + komentarz w `reply` + następne `question`; po 5. (albo `finish`) → `next: "finish"` + `result`. **exam** — 3 pytania, każde z dokładnie jednym dopytaniem (bez ocen po drodze); po 3. dopytaniu (albo `finish`) → `result` z `pct`. Ocenę w skali przedmiotu liczy apka (`gradeFor`); serwer daje tylko `pct` = średnia punktów 0–100 z modelu.

Odpowiedź 200: `{ reply, next: "question" | "followup" | "finish" | "end", question?: { n, text }, pointId?: "<topicId>:p3", verdict?: "ok" | "partial" | "wrong", feedback?: { good[], gap[], wrong[], source?: { topicId, level, feed } }, result?: { pct, score: { ok, total }, perQuestion: [{ q, verdict: "DOBRZE" | "PRAWIE" | "ŹLE", note, pointId? }], gaps: [{ title, topicId, level, feed, pointId? }] }, quota: { day, used, limit, remaining } }`. Teksty: zwykły tekst bez `<>` i emoji, ≤ 600 znaków (apka i tak je escapuje). Werdykt pytania z punktów: ≥ 70 DOBRZE, ≥ 40 PRAWIE, mniej ŹLE. Etykiety z kontekstu (`T1.l2.f1`, `T1.p3`) serwer zamienia na id i odrzuca, gdy nie istnieją. Model odpowiada wyłącznie z materiału ucznia; tekst ucznia trafia do promptu jako dane (JSON w `<rozmowa>`), nigdy jako polecenie.
